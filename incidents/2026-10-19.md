## Root cause

Commit `b22eb5b591ade5e5bc75c185c2ad92d7f0c878a3` changed `vite.config.ts` from reading `BASE_URL` to reading `PUBLIC_BASE_URL`, but the deploy workflow continued to pass `BASE_URL`. The build therefore used Vite's `/` default instead of `/Repstack/`, so the deployed page referenced assets outside the GitHub Pages project path and the application did not load. The HTTP probe still passed because GitHub Pages served the HTML. The deployment workflow's end-to-end tests run only after deployment, so a successful build could publish the broken page before those tests caught it.

## Blast radius

Visitors to the production site could load the HTML but not the app while the broken deployment was live. Locally stored user data was unaffected.

## Remediation

The health-check pipeline automatically redeployed the last green commit, `f182c4fa842fe4def071e47978ce2dd42589375e`; the deployment and E2E tests passed. A post-rollback health check has not run yet, so service restoration remains unverified. A human must step in if it fails or a later health check remains red.

## Permanent fix

Restore the Vite config to read `BASE_URL`, matching the variable the deploy workflow already passes. This preserves the working GitHub Pages project base path without changing the deploy workflow.
